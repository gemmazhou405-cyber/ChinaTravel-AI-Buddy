# ChinaEase page quality and top-five search objective

Effective: 2026-10-23. User direction: improve existing pages deeply, prioritise quality over page count, and work towards positions 1–5 for relevant searches. These positions are a target, not a forecast or guarantee.

## Daily work

Choose one existing high-value page for a complete task review. Start from prospective China tourists and the specific problem they need to solve. Keep the 240-hour calculator and travel budget as strategic priorities; include Amap, DiDi and other practical preparation pages when actual query exposure or a confirmed task gap supports the choice. Do not select a page simply because its average position looks good.

Read the current production page and latest main, the exact-page tracking record, actual available GSC data and the competing answers. State the page's primary job, candidate queries, evidence scope, competing page jobs, unmet tasks and the reason for today's choice. Search retrieval is not a target-country/device Google top-five ranking audit. Leave unavailable volume, difficulty, exact-page query positions and hidden-query relevance unknown.

Review the entire task, not just the paragraph being edited. Each review must address:

1. Intent: one clear primary job, with the answer and next step easy to find.
2. Completeness: requirements, supported step sequence, success check, common failure branches and usable alternatives.
3. Evidence: current primary sources, scoped source-check dates and explicit unknowns; real screenshots and device/version/date records only when supplied or actually tested.
4. Original value: a useful diagnostic, verified example, calculation, comparison, local observation or other concrete help that resolves a gap. Extra words, an FAQ, a date change or a generic warning alone do not qualify.
5. Usability: readable mobile layout, working contents links, visible controls, valid examples and accessible labels. Check loading, layout stability and interaction latency where measurable; distinguish local tests from field Core Web Vitals. Profile a suspected bottleneck before changing architecture, and do not call a large-bundle warning a measured field failure.
6. Trust and conversion: accurate publisher/author claims, a visible contact/service route, clear free versus paid scope and no invented biography, testimonial, photo, test or delivery promise.
7. Architecture: each adjacent page has a distinct job; same-topic pages are not automatically cannibalisation. Merge only after checking unique content, query evidence where available and the value of retiring a URL. Preserve useful content and functional tools before a permanent redirect. Related guides should usually contain 5–8 relevant links; this is an editorial rule, not a Google threshold.
8. Rendering and measurement: meaningful raw HTML, parity with React, correct canonical/index directives, schema matching visible content, and privacy-safe funnel events. A contact-link click is not an enquiry, delivered email or sale.

Record a specific before/after finding for each applicable dimension, including unchanged or unknown items. Do not manufacture edits to meet a daily quota. If the current page lacks a new verified gap or is in an observation window, complete its review, record the evidence gap and work on another supported page or a confirmed regression. Maintain a queue of full page reviews, not a queue of superficial paragraph additions.

## Release and observation

Implement authorised reversible improvements, run relevant build/type/lint and task regressions, inspect the final rendered page, then publish to main using a current-head lease and the existing Cloudflare deployment. Preserve other concurrent work and historical observations. Record actual code SHA, deployment and formal-page evidence. A successful build or HTTP 200 is not evidence of Google indexing, recrawl, ranking or click improvement.

Keep full-guide review dates separate from sitewide navigation/service-block changes. Advance lastmod for genuine main-content changes; do not refresh every article's review date when shared navigation changes. Record sitewide interventions as overlapping influences on existing tests.

Measure exact page × exact query with matching Web/country/device/date conditions where data exists. The desired range is positions 1–5. Track relevant impressions, clicks, CTR and actual enquiries/conversions alongside rankings. Preserve complete 7-day and 28-day windows and equal adjacent reference periods. Add later recrawl-based windows when needed. Do not interpret a one-day fluctuation or incomplete window as success or failure.

## Evidence that needs the owner

Real phone screenshots and observations must include device, OS, app version and test date, with sensitive data removed. Existing source-backed guides must not be presented as owner-tested until that evidence exists. Manual mailbox-forwarding delivery and external service fulfilment cannot be established by a mailto link, DNS record or HTML string alone. Keep these gaps explicit while completing independent code and content improvements.
